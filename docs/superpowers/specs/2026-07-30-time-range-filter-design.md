# G端资讯监控自定义时间筛选设计规格

## 目标

为现有信息流增加服务端自定义时间范围筛选。用户可以按北京时间选择精确到分钟的开始和结束时间，并与关键词、来源筛选组合使用。

完成标准：

- 时间筛选由 `/api/feed` 和 D1 查询执行，不只过滤浏览器当前加载的数据。
- 用户选择的开始分钟和结束分钟均包含在结果内。
- 时间固定按 `Asia/Shanghai`（UTC+08:00）解释，不随浏览器时区变化。
- 关键词、来源、开始时间和结束时间可以任意组合。
- 缺少原始发布时间的记录按首次采集时间参与筛选。
- 无效范围返回明确错误，不执行数据库查询。
- 清除时间范围后恢复最近全部可用数据。

## 产品范围

### 包含

- 精确到分钟的开始时间和结束时间
- “应用”和“清除”操作
- 已应用时间范围的紧凑展示
- 服务端参数校验
- D1 参数化时间查询
- 桌面端和移动端响应式布局
- 时间解析、接口、数据库和交互策略测试

### 不包含

- 超过现有七天保留期的数据查询
- 预设范围按钮，如“最近一小时”或“今天”
- 跨时区选择
- 日历热力图、趋势图或导出
- 修改采集、刷新、去重和七天清理逻辑

## 交互设计

时间筛选保持信息流优先，不增加常驻大面板：

1. 工具栏增加一个“时间范围”按钮。
2. 点击后展开紧凑编辑区，包含“开始时间”“结束时间”“应用”“清除”。
3. 两个输入使用 `datetime-local`，精确到分钟。
4. 点击“应用”后验证范围并请求服务端；成功后编辑区收起。
5. 已应用时，按钮显示紧凑摘要，例如 `07-29 09:30 → 07-30 18:00`。
6. 点击“清除”移除开始和结束时间，并立即恢复未限定时间的信息流。
7. 时间范围与关键词、来源筛选共同生效；任一筛选变化后均使用完整筛选条件重新读取信息流。

桌面端时间编辑区与工具栏对齐。移动端独占一行，开始和结束输入纵向排列，避免压缩来源按钮和刷新按钮。

## 时间语义

- 所有输入固定解释为北京时间 `Asia/Shanghai`，即 UTC+08:00。
- 前端将 `YYYY-MM-DDTHH:mm` 转换为带 `+08:00` 偏移的 ISO 8601 参数。
- 开始时间包含所选分钟，从该分钟的 `00.000` 开始。
- 结束时间包含所选分钟，查询上界为下一分钟且不包含该时刻。
- 示例：`09:30` 至 `18:00` 实际查询 `[09:30:00.000, 18:01:00.000)`。
- 允许选择当前分钟；不允许选择尚未开始的未来分钟。
- 可选范围限制在服务端当前时间往前七天之内。

数据库统一使用：

```sql
COALESCE(published_at, first_seen_at)
```

作为筛选时间。这样有原始发布时间时优先使用原始时间，没有时回退到首次采集时间。

## 接口设计

`GET /api/feed` 增加两个可选查询参数：

- `from`：带 `+08:00` 偏移的开始分钟 ISO 时间
- `to`：带 `+08:00` 偏移的结束分钟 ISO 时间

约束：

- `from` 和 `to` 必须同时提供或同时省略。
- 必须为分钟精度且显式包含 `+08:00`。
- `from` 不得晚于 `to`。
- 两者不得早于当前七天保留边界。
- 两者不得晚于当前北京时间所在分钟。
- 参数错误返回 `400` 和可直接展示的中文错误。

解析成功后，接口向仓库层传递两个毫秒时间戳：

- `fromMs`：开始分钟时间戳
- `toExclusiveMs`：结束分钟时间戳加 60,000 毫秒

接口继续返回现有 `FeedResponse`，不修改响应结构。

## 数据查询

`listFeed` 的查询选项增加 `fromMs` 和 `toExclusiveMs`。存在时间范围时追加参数化条件：

```sql
COALESCE(published_at, first_seen_at) >= ?
AND COALESCE(published_at, first_seen_at) < ?
```

该条件与来源和关键词条件使用 `AND` 组合。排序仍按同一时间字段倒序，返回上限仍为 100 条。

所有时间值继续通过 D1 `bind` 传入，不拼接到 SQL 字符串中。

## 前端状态与数据流

前端区分两组状态：

- 编辑值：用户正在输入但尚未应用的开始和结束时间。
- 已应用值：当前请求实际使用的时间范围。

数据流：

1. 用户展开编辑区并修改时间。
2. 点击“应用”。
3. 前端按北京时间执行基本校验。
4. 校验通过后更新已应用值，并携带 `q`、`source`、`from`、`to` 请求 `/api/feed`。
5. 刷新完成后，仍使用当前已应用的完整筛选条件重新读取信息流。
6. 点击“清除”时同时清空编辑值和已应用值。

初始化和五分钟轮询行为不变。时间筛选只影响信息流读取，不影响四个来源的采集范围。

## 错误处理

- 只填写一个时间：提示“请同时选择开始和结束时间”。
- 开始晚于结束：提示“开始时间不能晚于结束时间”。
- 超出七天范围：提示“只能筛选最近 7 天的数据”。
- 选择未来分钟：提示“不能选择未来时间”。
- 参数格式或时区不正确：API 返回 `400`。
- 数据库或网络错误：沿用现有“筛选失败”错误状态，保留当前信息流。
- 无匹配数据：显示现有空状态，并明确当前筛选条件下没有内容。

## 验证方案

### 时间解析

- 北京时间字符串转换为正确毫秒时间戳。
- 开始分钟为包含边界。
- 结束分钟转换为下一分钟的排除边界。
- 当前分钟有效，未来分钟无效。
- 缺少一端、格式错误、非 `+08:00`、倒置范围和超过七天均失败。

### 数据库查询

- 开始边界上的记录保留。
- 结束分钟内的记录保留。
- 下一分钟边界上的记录排除。
- 缺少发布时间时使用首次采集时间。
- 时间、关键词和来源组合查询正确。

### 接口

- 合法 `from`、`to` 传递到仓库层。
- 非法范围返回 `400`，且不调用仓库层。
- 没有时间参数时保持现有行为。

### 前端与构建

- “应用”只在完整且合法的范围下执行。
- “清除”恢复未限定时间的信息流。
- 手动刷新和自动刷新后保留已应用范围。
- 桌面端和移动端控件不遮挡搜索、来源和刷新操作。
- 全量测试、TypeScript、lint 和生产构建通过。

## 风险与约束

- 数据仅保留七天，时间筛选不能恢复已经清理的记录。
- 接口默认最多返回 60 条、上限 100 条；时间范围内记录超过上限时仍按时间倒序截取。
- 中国标准时间没有夏令时，固定 `+08:00` 可避免浏览器时区差异。

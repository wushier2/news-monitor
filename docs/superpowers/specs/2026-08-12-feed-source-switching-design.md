# 信息流平台切换优化设计

## 目标

消除 36Kr、界面监管、界面时事和财联社之间切换时固定等待、内容跟不上和连续点击像卡住的问题。平台与时间筛选应立即请求；搜索输入仍保留 250ms 防抖。

## 已确认交互

- 点击平台后立即选中新平台并开始请求，不再等待 250ms。
- 请求期间保留旧消息流，整体轻微淡化，并在信息流标题区域显示“正在切换至××”。
- 新数据成功返回后一次性替换旧内容并恢复正常显示。
- 请求失败时继续保留旧内容，恢复正常透明度，并显示读取失败信息。
- 连续切换时取消上一次尚未完成的信息流请求，最终只允许最后一次选择更新页面。

## 请求结构

将目前合并在一个 `useEffect` 中的搜索、平台和时间筛选触发拆开：

1. 搜索词变化使用 250ms 定时器，期满后读取第 1 页。
2. 平台或已应用时间范围变化立即读取第 1 页。
3. 所有信息流读取共享一个当前请求控制器。开始新请求前中止旧请求；组件卸载时也中止当前请求。
4. 保留现有请求序号校验作为第二层保护，避免不支持中止或已进入响应解析阶段的旧请求覆盖新状态。

`requestFeed` 接收可选 `AbortSignal` 并传给 `fetch`。中止属于正常切换流程，不显示错误，也不清除现有消息流。

## 状态与显示

新增独立的筛选加载状态，不复用分页加载状态：

- `filterLoading` 仅表示搜索、平台或时间筛选正在读取。
- 信息流容器在 `filterLoading` 时增加淡化样式，并继续保留旧文章，避免布局跳动。
- 标题右侧优先显示“正在切换至××”；搜索或时间范围变化时显示“正在更新筛选结果…”。
- 来源按钮保持可点击，允许用户快速改选；分页按钮在筛选请求期间禁用，避免同时改变筛选和页码。

## 边界

- 不增加客户端缓存，不调整 `/api/feed`、数据库、采集和排序逻辑。
- 不改变分页每页 50 条、日期分组或自动刷新周期。
- 自动刷新和补采完成后的信息流重载也使用同一请求取消机制；最新用户筛选始终优先。
- 初次加载仍使用现有全页加载状态，分页继续使用现有分页加载提示。

## 测试与验收

通过可独立测试的触发策略和请求协调逻辑验证：

1. 搜索变化返回 250ms 延迟，平台和时间变化返回 0ms。
2. 新请求开始时旧控制器被中止。
3. 被中止的请求不产生读取错误提示，也不覆盖最后一次结果。
4. 普通失败继续保留现有信息流并显示错误。

完成后运行聚焦测试、全量测试、类型检查、代码检查和构建，并在本地页面验证四个平台连续切换、搜索、时间筛选和分页。平台单次切换目标为接近接口实际耗时，不再包含固定 250ms 等待。

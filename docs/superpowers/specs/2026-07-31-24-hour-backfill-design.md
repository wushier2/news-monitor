# 过去 24 小时补充采集设计

## 目标

为 G端资讯监控增加一次性补充采集能力。用户在页面手动触发后，系统尽最大可能采集点击时刻向前滚动 24 小时内的完整信息，并明确报告每个平台的实际覆盖范围、完整度和失败原因。

首版默认同时补采现有四个来源：36Kr 宏观、界面监管通报、界面时事追踪和财联社头条。单个来源失败不得阻断其他来源。后端接口和采集核心同时支持可选 `sourceId`，为后续增加单个平台补采入口预留能力。

## 非目标

- 不把补充采集改成自动启动任务或定时任务。
- 不替换现有每 5 分钟普通采集流程。
- 不承诺第三方平台无法访问时仍然实现绝对完整。
- 首版不增加任意自定义补采时段。
- 首版不引入外部任务队列、搜索引擎或第三方聚合数据源。

## 完整性定义

每次任务在创建时固定时间窗口：

- `windowEnd`：用户点击启动按钮的时刻。
- `windowStart`：`windowEnd - 24 小时`。

任务执行期间不得移动该窗口。

每个来源独立产生以下状态：

- `running`：仍在翻页。
- `complete`：已确认翻到 `windowStart` 或更早，或者平台明确返回没有更多数据且可用历史已全部读取。
- `partial`：任务取得部分数据，但因限流、解析异常、安全页数上限、连续空页、重复游标或时间信息不足，无法确认完整覆盖 24 小时。
- `failed`：第一页即无法请求或无法解析，没有形成有效覆盖。
- `interrupted`：服务在任务运行期间重启或进程退出。

只有存在明确采集证据时才能显示“完整”。任何无法确认的情况必须降级为“部分完成”或“失败”。

## 总体架构

### 分平台分页适配器

为每个来源实现相同的分页契约：

```ts
interface BackfillPageRequest {
  cursor: string | null;
  windowStart: number;
  windowEnd: number;
}

interface BackfillPageResult {
  items: NormalizedItem[];
  nextCursor: string | null;
  exhausted: boolean;
}
```

适配器只负责平台请求、分页游标和页面解析，不负责数据库状态、任务调度或完整度汇总。36Kr、界面新闻两个频道和财联社分别维护独立适配器，以隔离第三方接口变化。

### 补采服务

`BackfillService` 接收固定时间窗口和来源列表，为每个来源顺序翻页：

1. 从最新页开始。
2. 解析并规范化本页数据。
3. 筛选出发布时间处于 `[windowStart, windowEnd]` 的记录。
4. 使用现有规范化 URL 和去重键幂等入库。
5. 保存逐来源进度。
6. 当最早发布时间达到窗口开始、平台耗尽或触发安全停止条件时结束该来源。

最多同时执行两个来源；同一来源必须串行翻页。同一来源的相邻页面请求至少间隔 500 毫秒。遇到 429 或 5xx 时最多重试两次，优先遵守 `Retry-After`，否则分别等待 1 秒和 2 秒。

### 后台任务执行器

`BackfillRunner` 在当前本地服务进程内后台执行任务，HTTP 启动请求不等待全部补采结束。任务和逐来源进度持久化到 D1，页面通过轮询读取状态。

同一时刻只允许一个补采任务运行。重复启动请求返回当前运行任务，不创建并行任务。补采运行期间，普通 5 分钟采集跳过上游请求，避免重复抓取和限流；信息流读取、搜索、筛选和分页不受影响。

任务状态与执行器分离，使未来迁移到 GitHub Actions、Cloudflare 队列或定时任务时无需重写平台适配器和补采服务。

## 数据模型

新增 `backfill_runs`：

- `id`
- `requested_source_id`，全部来源时为空
- `window_start`
- `window_end`
- `started_at`
- `finished_at`
- `status`：`running | complete | partial | failed | interrupted`
- `created_at`

新增 `backfill_source_runs`：

- `run_id`
- `source_id`
- `status`
- `cursor`
- `pages_fetched`
- `items_fetched`
- `items_in_window`
- `items_inserted`
- `items_existing`
- `earliest_covered_at`
- `error`
- `updated_at`

`run_id + source_id` 建立唯一索引。任务总状态由各来源状态汇总：全部完整为 `complete`；至少一个来源获得数据但并非全部完整为 `partial`；全部失败为 `failed`。

补采启动时，将数据库内遗留的 `running` 任务标记为 `interrupted`，避免服务重启后误报仍在运行。

## 数据流与停止条件

每个来源默认最多追踪 100 页。以下任一条件触发停止：

- 本页最早有效发布时间小于或等于 `windowStart`：标记完整。
- 平台明确没有下一页：标记完整。
- 达到 100 页：标记部分完成。
- 连续两页没有获得新的唯一记录：标记部分完成。
- 下一游标与当前游标相同或已访问过：标记部分完成。
- 上游返回 429、不可恢复错误或页面无法解析：第一页失败时标记失败，否则标记部分完成。
- 记录缺少发布时间且无法证明已经覆盖窗口开始：标记部分完成。

只保存发布时间位于固定窗口内的信息。早于窗口的数据只作为“已覆盖到窗口边界”的停止证据，不写入本次补采范围。晚于 `windowEnd` 的记录忽略。

每页入库前查询对应去重键是否已经存在，以准确区分 `items_inserted` 和 `items_existing`。入库仍使用现有 UPSERT 逻辑，保证与普通采集并发或重复执行时不会产生重复记录。

## API 契约

### 启动任务

`POST /api/backfill`

请求体：

```json
{}
```

未来单平台入口使用：

```json
{ "sourceId": "36kr-macro" }
```

成功创建返回 HTTP 202 和任务编号。已有任务运行时同样返回 HTTP 202，但标明 `reused: true` 并返回现有任务。

### 查询状态

`GET /api/backfill/:runId`

返回固定时间窗口、任务总状态和逐来源状态。前端只展示接口给出的完整度，不自行根据数量推断。

非法来源返回 HTTP 400；不存在的任务返回 HTTP 404；数据库或任务启动异常返回 HTTP 500。

## 页面交互

工具栏在“立即刷新”旁增加“补采过去24小时”按钮。

点击后显示简短确认，说明该操作会访问四个来源并可能持续数分钟。确认后：

- 按钮变为“补采进行中”并禁用重复启动。
- 工具栏下方展开补采状态面板。
- 面板显示总任务状态，以及每个来源的状态、页数、读取条数、新增条数和最早覆盖时间。
- 页面每 1 秒轮询任务状态，但正常信息流交互保持可用。
- 完成后自动重新加载当前筛选条件的第 1 页。
- 结果面板保留到下一次补采，页面刷新后从数据库恢复最近任务。

后续单平台补采在来源结果旁增加“单独补采”按钮，调用相同启动接口的 `sourceId` 参数。

## 错误处理

- 单个平台失败只影响该平台状态。
- 已成功入库的数据不因后续失败回滚或删除。
- 错误信息限制长度并去除多余空白，避免把上游完整响应写入数据库或页面。
- 后台任务中的未处理异常必须落库为任务失败状态，不能静默终止。
- 普通采集因补采占用而跳过时返回明确的忙碌状态，不将其记录为来源失败。
- 用户可在任务结束或中断后重新发起补采，去重逻辑保证重复执行安全。

## 测试与验收

自动测试使用固定网页或 JSON 样本，不依赖实时第三方网站：

- 各来源多页解析、游标推进和耗尽判断。
- 固定 24 小时时间边界及窗口外记录过滤。
- 达到窗口边界时停止。
- 429、解析失败、第一页失败和中途失败。
- 100 页上限、连续空页和重复游标。
- 单来源失败不影响其他来源。
- 重复记录不重复入库，并准确统计新增和已存在数量。
- 任务状态持久化、页面刷新恢复和服务重启中断处理。
- 补采期间普通采集跳过。
- 全部来源和可选单来源 API 输入契约。
- 前端按钮禁用、进度展示和完成后回到第 1 页。

本地验收使用真实服务执行一次过去 24 小时补采，逐来源检查：

- 状态不是无依据的“完整”。
- 最早覆盖时间与停止原因一致。
- 数据库中没有重复去重键。
- 新增数量与实际数据库变化一致。
- 补采期间信息流仍能搜索、筛选和翻页。

## 实施边界与风险

第三方平台没有向本项目提供稳定性承诺。分页接口、签名或 HTML 结构变化会使单个适配器降级为部分完成或失败，但不得影响其他来源和已入库数据。

首版需要先用各平台当前真实页面请求确认分页参数或游标，再固化相应样本和适配器测试。若某个平台当前无法提供可追溯到 24 小时前的入口，系统必须如实报告其可达到的最早覆盖时间，不能用重复首页请求伪装完整补采。
